01 — Orientation

What Lakbay is

A Philippines-first holiday-booking platform, architected as six repos instead of one monolith — each repo does exactly one job, and nothing reaches into another repo's database.

Lakbay sells curated Philippine holidays across four themed collections — Philippines-only by deliberate choice, not by naming accident: "Lakbay" means "journey" in Filipino, so the brand doesn't foreclose a future non-PH destination if that's ever revisited. The platform is modeled on a real enterprise pattern (Hotelplan's ECMS/PCMS/Sphinx-API estate) but re-architected for a small team: content is authored in one place, searched through a purpose-built read model, transacted in an isolated booking service, and presented by a single headless frontend.

The six repos

📖 Lakbay.Docs

Platform plan, ADRs, devlog. No runtime role — this is the "why" for everything else.

🧩 Lakbay.Contracts

The shared GraphQL SDL schema, plus generated C#/TS types. Never a running service.

✏️ Lakbay.Cms

Umbraco 18 — content + product catalog authoring. The source of truth.

🔎 Lakbay.AvailabilityApi

HotChocolate + MongoDB. Denormalized, faceted read model — what the storefront actually queries.

🧾 Lakbay.Booking

Orders, basket, availability, payment — deliberately isolated (Phase 4, not started).

🖥️ Lakbay.Web

Next.js + Redux Toolkit + RTK Query. Owns 100% of presentation, headless throughout.

Where things stand: Phases 0–3 are complete and verified live, both trees (Products + Content). The catalog carries real accommodation and included/optional-activities data per product (ADR-0016, matching how Inghams/Inntravel/Santa's Lapland actually sell a holiday) across 14 real Philippine destinations. Phase 4 (real checkout) is blocked on a PayMongo sandbox account. See 04_TASKS.md in Lakbay.Docs for the live checklist.

Architecture: CQRS at platform scale

Not one decision but the same pattern applied twice — once across the whole platform, once again inside Lakbay.Booking.

Read and write sides never touch the same database — sync happens over events, not shared storage.

Why this shape, not a monolith:

  • Read-heavy publishing vs. write-heavy transactions have different performance profiles — Umbraco's cache is built for read-heavy publish-then-cache workloads; basket writes are the opposite. Mixing them risks lock contention at checkout, the worst possible moment.
  • General content indexing and faceted product search are different tools — a dedicated search service (modeled on Hotelplan's Manticore-backed Sphinx-API) handles filtered search precisely because a CMS's own index isn't built for it at scale.
  • A frontend coupled to a CMS's render pipeline can't be built or tested independently — headless-everything plus one shared contract means Lakbay.Web runs, builds, and demos against Lakbay.AvailabilityApi alone, no other service required.

Data flow & user journey

Two journeys worth holding in your head: what a shopper does, and what an edit does.

A shopper's path through Lakbay.Web

Homepage
/

Four product-line cards, driven entirely by useGetProductLinesQuery — no hard-coded lines. Adding a 5th line to the schema needs zero frontend code changes.

Collection
/collections/[code]

Products in one line via useGetProductsQuery({ productLine }) — real photos, price-from, duration, sold-out state.

Detail
/holidays/[slug]

Full itinerary, board basis, price bands, hero image, a named accommodation card, and included-vs-optional activity lists (ADR-0016). "Book this holiday" is an honestly-disabled button — Phase 4 isn't built, so it doesn't pretend to be.

Phase 4
Checkout →

Not built. Will call Lakbay.Booking directly; catalog data keeps coming from Lakbay.AvailabilityApi throughout — no repointing.

No redeploy, no code change — publishing in the CMS is the only action a content editor ever takes.
Why field-scoped, not a full document replace: Product has two independent writers — Cms owns catalog fields, Lakbay.Booking will own availableCount (Phase 4). A blind overwrite from either side would clobber the other's data. See ADR-0014.

05 — Running it locally

Setup walkthrough

One dependency-ordered pass, first time on this machine. Every command here has actually been run — nothing is assumed.

Prerequisites

.NET SDK 10, Node.js 20+, Docker Desktop, Azure Functions Core Tools (func).

winget install Microsoft.DotNet.SDK.10
winget install OpenJS.NodeJS
winget install -e --id Docker.DockerDesktop
npm install -g azure-functions-core-tools@4 --unsafe-perm true
Docker Desktop's first launch: complete its onboarding screen before trying docker commands. If docker ps hangs for minutes, check %APPDATA%\Docker\settings-store.json for "DisplayedOnboarding": false — that's the actual blocker, not a slow backend.

Lakbay.Contracts — the shared schema

No dependencies, no database. Everything else references this.

cd Lakbay.Contracts/typescript && npm install && npm run codegen && npx tsc --noEmit
cd ../csharp && dotnet build

Lakbay.Cms — Umbraco 18

SQL Server, then user-secrets for both the DB connection and the Service Bus emulator.

cp .env.example .env   # set DB_PASSWORD
docker compose up -d
cd src/Lakbay.Cms.Web
dotnet user-secrets set "ConnectionStrings:umbracoDbDSN" "Server=localhost,1433;Database=umbracoDb;User Id=sa;Password=<yours>;TrustServerCertificate=true"
dotnet user-secrets set "ConnectionStrings:ServiceBus" "Endpoint=sb://localhost;SharedAccessKeyName=RootManageSharedAccessKey;SharedAccessKey=SAS_KEY_VALUE;UseDevelopmentEmulator=true;"
dotnet run

First run only: complete Umbraco's install wizard at https://localhost:44330/umbraco — real email, real password, your choice. Never scripted, never recorded anywhere.

Lakbay.AvailabilityApi — read model + sync consumer

Mongo and the Service Bus emulator together, then the Sync function before the query API.

docker compose up -d   # mongo + servicebus emulator
cd src/Lakbay.AvailabilityApi.Sync && func start
# — separate terminal —
cd src/Lakbay.AvailabilityApi.Api && dotnet run   # :5170

Lakbay.Web — the storefront

npm install && npm run build && npm run dev   # :3000

Prove it end to end

With all five running: open Lakbay.Cms's backoffice, edit a product's summary, publish. Reload the same product's detail page in Lakbay.Web — the new text should appear with zero code change and zero redeploy. That's Phase 3's actual proof, not just "it compiles."

Architecture decision records

The "why" behind every structural seam, in the order they were made. Full text lives in Lakbay.Docs/docs/adr/.

0001
Unify ECMS + PCMS
Content and product-catalog trees live in one Umbraco solution — the biggest cost lever vs. a Hotelplan-style split.
Cms
0002
CQRS inside Booking
Commands and queries as separate MediatR handlers.
Booking
0003
Separate booking data
Bookings never live in Cms's database — read-heavy publish vs. write-heavy transactions don't mix.
BookingCms
0004
.NET, not Node, for the search service
One backend language across the whole platform (Cms, Booking, Contracts, AvailabilityApi).
AvailabilityApi
0005
Local SQL Server, not Azure SQL
Azure SQL Database has no offline edition — Docker locally, Azure only once a live environment exists.
CmsBooking
0006
Headless CMS, no Razor UI
Cms never renders a page — Lakbay.Web owns 100% of presentation, on purpose.
CmsWeb
0007
AvailabilityApi is real, not a mock
Permanently deployed, modeled on Hotelplan's api-sphinx — not a disposable throwaway.
AvailabilityApi
0008
Real-time availability propagation
Booking → Service Bus → AvailabilityApi → SignalR → Web — no polling.
BookingAvailabilityApiWeb
0009
Split query-serving from event-consumption
Two deployables in one repo so sync load never competes with shoppers' queries.
AvailabilityApi
0010
Last-write-wins sync ordering
A sourceUpdatedUtc timestamp guard, since Service Bus doesn't guarantee strict ordering.
AvailabilityApi
0011
Atomic availability decrement
A single conditional SQL UPDATE prevents double-booking — never read-then-write.
Booking
0012
Block rendering in React
A block registry maps Umbraco element-type alias to React component — no Razor involved.
WebCms
0013
Cms sync trigger is Service Bus
Reuses the Sync function ADR-0009 already scaffolded — one consumption mechanism for the whole platform.
CmsAvailabilityApi
0014
Product's dual-writer ordering fix
A second internal ordering field so Cms and Booking's writes can never falsely reject each other.
AvailabilityApi
0015
Content sections are JSON, not a real Block List
A real Umbraco Block List round-tripped correctly through SQL but the Content Delivery API silently returned zero items — pivoted to the already-proven JSON-in-Textarea pattern.
CmsWeb
0016
Accommodation + included/optional activities on Product
Researched Inghams/Inntravel/Santa's Lapland — a holiday is a named stay plus a split of included-vs-optional activities, not just a destination.

09 — Finding your way

For AI agents

If you're an AI coding agent picking up work here, this is the fast path — read this before touching code.

Reading order

  • Lakbay.Docs/docs/01_CLAUDE.md — the platform operating manual. Wins over anything else if they conflict, unless the user overrides it explicitly in-session.
  • 04_TASKS.md — current phase and status, more current than this page's snapshot.
  • The repo's own CLAUDE.md — points to exactly which ADRs that repo must honor. Don't read every ADR for every task.
  • 05_DEVLOG.md's most recent entries — what changed since the build plan was last touched.

Working conventions this codebase actually enforces

  • Every non-obvious structural choice gets an ADR — a new abstraction, a SOLID trade-off, a design pattern. Not optional here.
  • Verify by running it, not by reading the code. Most real bugs this project found (see Troubleshooting) were only caught by actually publishing, querying, or booting something — a clean compile was never treated as proof.
  • Kill processes by exact PID, never by name — this codebase has been bitten twice by a blanket taskkill /IM dotnet.exe killing unrelated services.
  • Open items get surfaced, not silently resolved — see 01_CLAUDE.md §6 for the standing list (GraphQL-on-Umbraco package choice, GitHub remotes, business model).
